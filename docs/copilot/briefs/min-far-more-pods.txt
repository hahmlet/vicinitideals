Steph ruled 2026-11-04 (flats/config/rulings.yaml id 2026-11-04-min-floor-area-more-pods): a minimum floor area ratio that one pod is too small to meet is RED only when there is clearly no room for the pods it would take; if there clearly is room, or it is unclear, YELLOW. This mirrors the existing building-frontage rule 2026-10-21-wide-lot-frontage-more-pods (flats/score/screen.py: _pods_to_fill, MORE_BUILDINGS, flag FRONTAGE-MORE-BUILDINGS). Read both rulings first.

(a) The general `min_far` check (flats/score/screen.py: SOFT_FLOOR_CHECKS ~L154 includes "min_far"; the FAR-MIN flag / CLOSER_LOOK_MIN_FAR ~L2615 and ~L3210): a miss is ALWAYS YELLOW.

CHANGE (one rule for both):
1. Floor area the code needs: need_sqft = required FAR x the measured lot area (for (b) the overlay part, `measured` in pdx_overlays; for (a) whatever area the min_far check already measures on).
2. Pods it would take: n = ceil(need_sqft / one pod's floor area) (the same floor area the check credits for one pod). n >= 2 whenever one pod misses.
3. Clearly no room: RED only when even the most lenient packing cannot hold n pods -- the buildable ground (the lot, or for (b) its overlay part, inside the resolved setbacks; use the screen's own envelope/buildable-area figure if one exists -- grep screen.py / flats/fit for envelope, buildable, area_sqft) is smaller than n x the pod's footprint area (width x depth). Ignore parking, separation and shape for this test: that is what makes it "clearly".
4. Otherwise (room for n pods, or the buildable area unknown/unmeasured): YELLOW, held out of GREEN with a flag that it needs more than one building (reuse FAR-MIN / CLOSER_LOOK_MIN_FAR for (a); for (b) make pdx_min_far behave the same way -- a held/unmeasured outcome or a soft-floor check that yields YELLOW with its flag -- instead of a RED Bind). Never GREEN on a missed minimum.
5. A pod that meets the minimum on its own is judged exactly as today.
